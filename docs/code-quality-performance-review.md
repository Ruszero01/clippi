# Clippi 第三批性能优化单次执行方案（剪贴板捕获增量合并）

日期：2026-08-13

问题识别基线：`e9c4668636e14c43fb418931a8aba2e2d6589b05`（两轮优化前的原始代码）

评估基线：`3ba51ce`（当前分支 HEAD；包含两轮优化、Word 剪贴板 HTML 预览修复和发布说明更新）

未来执行基线：第三轮恢复时以合并后的最新 `main` HEAD 重新确认，不预建实施分支

文档状态：已评估，暂缓执行

## 1. 前两轮优化摘要

### 1.1 第一轮：核心热路径止损

提交 `e01d318`（`perf: reduce main-thread work in core hot paths`）完成四项优化：

- 卡片渲染复用文件状态缓存，移除正文预览和底部信息中的重复同步路径探测。
- 窗口几何保存改为 500 ms trailing-edge 防抖、原子写入和失败退避，隐藏与退出前强制刷新。
- 剪贴板入库复用同一内容哈希的查询结果，裁剪只读取待删除 ID，标题栏四次统计查询合并为一次聚合查询，并移除入库后的无效标签重载。
- 搜索输入增加 150 ms 防抖，拼音编码和匹配过程复用中间结果，减少临时分配。

交付规模：修改 8 个生产模块，生产代码净增 169 行；无新增依赖、轮询循环、常驻线程或缓存状态机。自动验证结果为 `cargo test` 508 passed、0 failed，Clippy 零告警，`git diff --check` 通过。窗口拖动、断开映射盘路径、快速搜索和连续复制的真机验证仍由用户执行。

### 1.2 第二轮：复制/粘贴使用时间增量更新

提交 `160d7d8`（`perf: incremental clipboard usage updates`）完成以下优化：

- 单条复制/粘贴复用已经读取的条目，不再重复按 ID 读取，也不再因更新时间变化执行完整 `reload_items()`。
- 批量使用统一为一次事务、一个 `updated_at` 和一次内存重排；数据库按最多 500 个 ID 分块更新并保证失败回滚。
- `ClipboardListView` 只同步受影响条目的 `updated_at`，让条目与高度缓存成对重排；不安全场景最多回退一次全量同步。
- 新增 10,000 条历史数据基线与 19 个定向测试，覆盖排序、筛选、事务、同步范围、选择恢复和 UI 安全门。

本机基线（列表窗口 200，预热后 10 次中位耗时）：

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单条使用，按 `updated_at` 排序 | 6,259 µs | 45 µs |
| 单条使用，按 `created_at` 排序 | 6,284 µs | 38 µs |
| 单条使用，收藏优先关键词搜索 | 40,805 µs | 46 µs |
| 批量 20 条 | 813,000 µs | 124 µs |
| 批量 100 条 | 4,083,387 µs | 464 µs |

交付规模：仅修改 `src/core/db.rs`、`src/state/app.rs`、`src/ui/clipboard_list.rs` 三个生产模块，生产代码净增 278 行，未新增依赖或并发协议。一次并行全量测试为 526 passed、0 failed、1 ignored；后续串行全量测试遇到既有 WebDAV socket 时序偶发失败，该问题可在执行基线复现且单测连续 5 次通过，因此未扩展第二轮范围。Clippy 零告警，`git diff --check` 通过。第二轮列出的六项真机验证仍由用户执行。

## 2. 第三批选题结论

第三批只处理“本地剪贴板捕获成功后刷新历史列表”的放大链，不建立通用增量列表框架。

该问题在原始基线 `e9c4668` 中已经存在：

1. `GpuiClipboardService::poll_state()` 每 200 ms 从 pending 缓冲区取出捕获项，逐条 `upsert()`。
2. 只要本批存在成功写入，原始代码就会裁剪超限条目，然后执行 `state.reload_items()` 和 `state.reload_tags()`。
3. 原始 `reload_items()` 会重新查询当前窗口（默认 200 条）、批量填充标签并刷新标题栏统计；第一轮只移除了无效标签重载并压缩了查询次数，没有消除列表重载。
4. `WindowManagerEvent::ClipboardChanged` 到达 `RootView` 后，`visible_items()` 再克隆全部可见条目，`ClipboardListView::set_items()` 再为全部条目计算卡片高度并重置选择状态。
5. 隐藏窗口时 `AppState` 与列表会主动清空以释放内存，但原始轮询不检查主窗口/快速窗口可见性；隐藏后的下一次外部复制会重新加载并克隆列表，使内存释放效果被提前抵消。

第二轮只优化“使用已有条目”的 `updated_at` 路径，没有改变新捕获、重复捕获、超限裁剪或异步内容回填的上述链路。第三批问题因此不是前两轮新增结构造成的。

必要性结论：第三轮存在真实问题，但不应按原方案整批立即实施。隐藏窗口捕获重新回填历史列表，直接抵消现有内存释放设计，属于高必要性止损；可见列表增量合并的收益依赖实测，P3 的额外状态协调成本目前高于已证明收益。

恢复执行时按以下顺序处理：

1. 必做：建立轻量基线，证明隐藏回填和可见刷新成本。
2. 必做：主窗口与快速窗口均隐藏时不回填内存列表。
3. 条件执行：仅当基线证明可见捕获有明显主线程成本时，实施无筛选列表增量合并。
4. 默认跳过：仅当 P2 后测量证明 UI 全量克隆或高度计算仍是主要瓶颈时，实施 P3。
5. 所有无法证明安全的场景统一回退一次现有全量刷新。

## 3. 本批优先级

### P0：建立捕获链路基线与结构性计数

恢复第三轮时，先在届时最新 `main` 上建立可重复基线，再决定是否修改生产代码。原始基线 `e9c4668` 只用于证明问题来源；实际优化前后耗时以届时执行基线和第三批最终代码比较，避免把前两轮收益重复计入第三批。

测试数据为 10,000 条普通文本历史，内存列表窗口为 200，至少覆盖：

- 可见主窗口捕获一条全新普通文本。
- 可见主窗口重复捕获当前窗口中部的一条记录，使其在 `updated_at` 排序下移动。
- 同一轮 pending 中连续处理 20 条记录，包含重复内容哈希。
- `sort_by_created = true` 下的新捕获与重复捕获。
- `max_items > 0` 且本次捕获触发非收藏条目裁剪。
- 主窗口与快速窗口均隐藏时捕获一条记录。

记录预热后至少 10 次运行的中位耗时，同时记录以下结构性信号：

- `reload_items()` 调用次数。
- 当前页查询和标签填充次数。
- `visible_items()` 全量克隆次数。
- `ClipboardListView::compute_sizes()` 处理的条目数。
- 隐藏捕获后 `AppState.items` 与列表是否保持为空。

基准不得调用真实系统剪贴板、模拟 Ctrl+V、播放声音或触发 URL 网络任务；使用测试辅助入口复现“upsert 成功后的刷新阶段”。不新增 Criterion 等依赖，不把机器耗时写成 CI 硬阈值。

P0 使用测试内计数和简单中位耗时即可，不建设独立 benchmark 框架。若基线无法稳定证明隐藏回填，停止全部生产代码修改；若只能证明隐藏回填而无法证明可见刷新有明显成本，则只实施 P1 的隐藏快速路径并停止。

### P1：让捕获结果携带最小持久化增量，并增加隐藏快速路径

把 `poll_state()` 的“是否变化”布尔结果收敛为捕获专用结果，表达以下三种状态：无变化、仅持久化、需要刷新视图。具体类型名可按现有命名调整，但不得演化为全局事件总线。

1. `Database::upsert()` 或其捕获专用封装返回稳定 ID 和“新增/更新”结果；随后只按该 ID 读取一条带标签的列表投影，得到数据库实际保留的收藏、备注、热键、创建时间和标签。不得直接用监听器生成的 `ClipboardItem` 覆盖这些持久字段。
2. 同一轮 pending 按内容哈希/稳定 ID 去重，只保留每个条目的最终持久化结果；每次成功检测仍保持现有复制提示音和 `sync_dirty` 语义。
3. 继续复用当前 `prune_excess_non_favorites()` 返回的已删除 ID；该返回值来自第一轮实现，可以作为第三批机制，但不能作为第三批问题存在的证据。
4. 当主窗口和快速窗口均不可见时，只完成 upsert、裁剪、异步分析调度和同步脏标记，不调用 `reload_items()`、不回填 `AppState.items`、不发出列表刷新事件。下次打开主窗口或快速窗口时仍走现有完整加载。
5. 隐藏快速路径不得跳过 OCR/QR、缩略图、URL 元数据任务、复制提示音、裁剪或同步标记；只跳过当前不可见的内存与 UI 刷新。
6. 任一条目 upsert 失败时沿用现有逐条容错：失败条目不进入增量结果，已成功条目不回滚；不得顺带把捕获批次改造成跨条目的总事务。

### P2（条件执行）：仅在无筛选历史视图中增量维护 `AppState.items`

只有 P0 证明可见捕获的完整查询、克隆或高度计算造成明显主线程成本时才进入 P2。新增捕获专用安全门，仅同时满足以下条件时允许增量合并：

- 主窗口或快速窗口可见，且 `AppState.items` 已由窗口打开流程完整加载。
- 当前不是传输站视图。
- 类型、收藏、热键、标签和关键词筛选全部未启用。
- 本轮没有 OCR、QR、缩略图或 URL 标题完成等 `needs_reload` 信号。
- 每个成功 upsert 都取得了稳定 ID 和完整列表投影，裁剪也返回了确定的删除 ID。
- 当前排序只使用现有的 `updated_at` 或 `created_at` 语义。
- 开启“过滤非本机路径”时，本轮条目能够按现有规则明确判定；否则直接回退。

增量合并规则：

1. 先按 ID 移除本轮裁剪项，再按 ID 替换重复项或插入新项；同一 ID 只出现一次。
2. 对列表投影调用现有 `shrink_item_for_list()`，不把完整正文或大字段重新带回列表。
3. 按 `updated_at` 排序时稳定重排；按 `created_at` 排序时，新条目进入正确位置，重复条目保持其创建时间位置。
4. 结果长度截断到 `query_limit()`。若裁剪、边界补位或当前 ID 集合使正确的前 N 项无法仅凭本轮增量确定，则只回退一次 `reload_items()`，不追加边界查询协议。
5. 增量成功后只刷新一次标题栏聚合统计；不得重新引入四个独立统计查询。
6. 记录本轮新增/替换 ID，供列表视图一次性消费；该请求与第二轮的 usage 请求分开，完整 reload 必须清除两类待处理请求，避免跨事件误消费。

不在本批实现筛选条件下的成员资格判断。即使某个类型或关键词看起来可以局部判断，只要存在任一筛选维度，就走现有完整 reload。

### P3（默认跳过）：列表视图只同步捕获变化项和对应高度

P3 不属于第三轮默认完成条件。只有 P2 已实施，且复测证明 `set_items()` 的全量克隆或 `compute_sizes()` 仍占捕获主路径主要耗时时才进入。同步、清理、窗口打开、设置变化等其他来源继续使用现有全量 `set_items()`。

1. 从 `AppState` 取得一次性捕获请求，仅克隆新增/替换条目；未变化条目继续复用 `ClipboardListView.items` 中的所有权和原高度。
2. 删除已裁剪或因窗口截断离开的 ID，只为新增/替换条目调用卡片高度计算；条目与 `item_sizes` 必须成对移动。
3. 重排后按稳定 ID 恢复当前单选目标；沿用 `set_items()` 的现有可观察语义：捕获刷新会清除批量选择和悬停状态，开启 `auto_scroll_to_top` 时选择并滚动到最新条目，否则恢复此前选中 ID。
4. 快速粘贴窗口继续直接读取 `AppState.items`；捕获增量成功时只触发其重绘，不新增第二份快速窗口列表缓存。
5. 若列表 ID、长度、尺寸缓存或捕获请求与 `AppState` 不一致，立即回退一次 `set_items()`；回退后清空捕获请求，不允许下一帧重复回退。

停止条件：如果 P3 需要把全部 `ClipboardItem` 改成 `Arc`/`Rc`、建立通用 keyed-diff 引擎、修改虚拟列表组件或为不同事件建立 generation 状态机，则跳过 P3。P1 和 P2 仍可独立交付，并在结果中明确记录 UI 仍有全量克隆/高度计算。

## 4. 硬性范围约束

- P0 + P1 的生产代码净增不超过 **160 行**，修改模块不超过 `src/services/gpui_clipboard.rs`、`src/ui/window_manager.rs`、`src/state/app.rs` 三个。
- 仅当 P2 被基线触发时，总生产代码净增上限放宽至 **320 行**；P3 若被测量触发，总上限才可放宽至 **400 行**。
- 全部阶段允许修改的生产模块不超过以下 **7 个**：
  - `src/core/db.rs`
  - `src/core/filters.rs`
  - `src/services/gpui_clipboard.rs`
  - `src/state/app.rs`
  - `src/ui/window_manager.rs`
  - `src/ui/root.rs`
  - `src/ui/clipboard_list.rs`
- 不新增第三方依赖、数据库表、迁移、索引、后台线程、GPUI 轮询循环或任务队列。
- 不修改剪贴板监听频率、检测优先级、`skip_next` / `batch_pasting` 协议、系统剪贴板写入或粘贴模拟。
- 不改变 `updated_at` / `created_at` 排序语义、最大条目裁剪语义、收藏/标签/热键保留语义或同步范围。
- 不把第二轮 usage 增量请求改造成通用 mutation diff；捕获请求必须是独立、一次性、可回退的小协议。
- 任一优先级超出代码或模块预算时，保留更小的已验证阶段并停止，不扩大到相邻模块。

## 5. 明确不做

以下事项即使合理，也不进入第三批：

- 不在任意筛选、搜索或收藏优先结果中做新捕获增量成员判断。
- 不优化 OCR、QR、缩略图、favicon、URL 标题完成后的刷新；这些内容变化继续全量回退。
- 不改造同步合并、传输站、标签、收藏、备注、编辑、删除或设置变化的列表刷新。
- 不实现后台搜索、只读数据库连接、SQLite FTS5、keyset pagination 或扩大查询窗口。
- 不统一缩略图、应用图标、文件图标和 favicon 的缓存生命周期。
- 不处理孤儿缓存清理与并发写入之间的竞态；该问题是独立的正确性任务，需要覆盖所有缓存写入者，不能夹带在捕获列表优化中。
- 不拆分 `AppState`、`WindowManager`、`Database` 或 `ClipboardListView` 大模块。
- 不修改 release profile，也不做安装包体积优化。
- 不主动启动、关闭或替换用户正在运行的 Clippi 实例。

## 6. 实施顺序与停止规则

1. 第三轮恢复时，从最新 `main` 创建独立分支，确认工作区无其他改动，并重新核对捕获路径没有被后续提交改变。
2. 完成轻量 P0，记录隐藏回填、完整 reload、全量克隆和高度计算证据。
3. 完成 P1 的隐藏快速路径，先验证所有持久化与异步副作用仍执行。
4. 若 P0 未证明可见捕获有明显成本，到此停止并交付 P1。
5. 若基线触发 P2，完成无筛选 `AppState.items` 增量合并并验证安全门；复测后仅在 UI 仍是主要瓶颈时进入 P3。
6. 使用与 P0 相同的数据和入口复测，报告中位耗时和结构性调用变化。
7. 运行定向测试、全量测试、Clippy 和差异检查。

出现以下任一情况时立即回退到一次完整刷新，不继续扩大设计：

- 无法从 upsert 结果恢复数据库实际保留的稳定 ID 或持久字段。
- 当前内存列表没有完整加载，或列表与状态的 ID/高度缓存不一致。
- 需要为筛选、分页边界或异步内容回填新增第二套匹配逻辑。
- 需要跨线程传递 GPUI Entity、Window 或 UI 元素。
- P3 触发上一节的停止条件。

## 7. 验收条件

### 7.1 结构性验收

- 隐藏捕获成功后，数据库、裁剪、异步任务和同步状态正常，但 `AppState.items` 与列表保持释放状态。
- 可见、无筛选、无异步回填的捕获不调用 `reload_items()`，不查询完整当前页。
- 一轮 N 条捕获最多执行一次内存合并、一次稳定重排和一次标题栏聚合统计刷新。
- 重复捕获保留原条目的 ID、创建时间、收藏、备注、标签和热键，只更新当前 upsert 本来会更新的字段。
- `max_items` 裁剪项不会残留在状态或列表中；无法确定分页边界时只完整刷新一次。
- P3 若实施，未变化条目不被重新克隆，未变化卡片不重新计算高度；条目与高度始终配对。
- 任意筛选、传输站、异步内容完成或安全门失败均保持现有全量刷新语义。

### 7.2 自动验证

定向测试至少覆盖：

- upsert 新增与重复结果的稳定 ID，以及重复项持久字段保留。
- 同轮重复哈希/ID 去重和逐条失败容错。
- 主窗口、快速窗口均隐藏时不回填内存，但副作用不丢失。
- `updated_at` 与 `created_at` 两种排序下的新项插入和重复项替换。
- `max_items` 无裁剪、裁剪可安全合并、裁剪需回退三种路径。
- 任一类型、收藏、热键、标签或关键词筛选激活时回退。
- 非本机路径过滤、传输站和异步 `needs_reload` 信号回退。
- 完整 reload 清除捕获与 usage 两类待处理请求。

### 7.3 用户手工验证

由用户使用其当前运行实例或明确启动的测试版本执行：

1. 隐藏 Clippi 后连续复制文本、富文本和图片，再打开主窗口，确认最新记录、OCR/QR 调度和排序正常。
2. 主窗口可见且无筛选时复制新内容、重复复制旧内容，分别验证 `updated_at` 与 `created_at` 排序。
3. 设置较小 `max_items` 后连续复制，确认最旧非收藏条目被正确裁剪，收藏项不受影响。
4. 分别启用类型、收藏、热键、标签、关键词和“过滤非本机路径”，确认新捕获只影响应出现的结果。
5. 打开快速粘贴窗口后复制新内容，确认列表重绘、选择和高级粘贴模式正常。
6. 捕获图片和链接，等待缩略图、OCR/QR 与 URL 标题完成，确认回填后内容和卡片高度正常。
7. 在多选状态下发生外部复制，确认多选清除、单选恢复和自动滚顶行为与当前版本一致。
